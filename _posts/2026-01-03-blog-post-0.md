# Removendo Arquivos Indesejados de um Commit Git

## TL;DR (Resumo Rápido)

Commitou arquivos errados? Use este processo:

```bash
# 1. Identifique o commit anterior ao problemático
git log --oneline -5

# 2. Inicie rebase interativo marcando para edição
GIT_SEQUENCE_EDITOR="sed -i 's/^pick <hash>/edit <hash>/'" git rebase -i <hash-anterior>

# 3. Remova os arquivos indesejados
git reset HEAD^ -- arquivo1.txt arquivo2.txt

# 4. Refaça o commit sem os arquivos
git commit --amend --no-edit

# 5. Finalize o rebase
git rebase --continue
```

⚠️ **Atenção:** Só faça isso se ainda não deu push, ou esteja preparado para usar `git push --force`.

## O Problema

Você já passou por aquela situação onde fez um `git add .` apressado, commitou as mudanças e depois percebeu que incluiu arquivos que não deveriam estar naquele commit? Talvez foram notas pessoais, arquivos de configuração, ou até documentação que deveria estar em um commit separado?

Pois é, isso acontece com frequência, especialmente quando trabalhamos em múltiplas funcionalidades simultaneamente e esquecemos de revisar o que realmente está sendo commitado.

Neste artigo, vou mostrar como resolvi exatamente esse problema: **remover arquivos específicos de um commit mantendo as outras alterações intactas**.

## Um Exemplo Prático

Imagine que você tinha um commit chamado "fix: corrige validação de formulário" que deveria conter apenas 3 arquivos relacionados à correção:

- `src/components/LoginForm.tsx`
- `src/components/RegisterForm.tsx`
- `src/utils/validation.ts`

Porém, ao verificar o commit, você descobre que incluiu acidentalmente mais 4 arquivos:

- `CHANGELOG.md`
- `TODO.md`
- `docs/README.md`
- `scripts/test-data.js`

Esses arquivos não tinham nada a ver com a correção de validação e poluem o histórico do commit.

## Como Identificar o Problema

Primeiro, verifique o conteúdo do commit problemático:

```bash
git show --name-status <hash-do-commit>
```

Ou veja o histórico recente:

```bash
git log --oneline -10
```

No nosso exemplo, vamos supor que identificamos que o commit `abc1234` tinha arquivos extras que não deveriam estar lá.

## A Solução: Git Rebase Interativo

A ferramenta mais poderosa para reescrever o histórico do Git é o [**rebase interativo**](https://git-scm.com/book/pt-br/v2/Git-Tools-Rewriting-History). Ele permite editar, reordenar, combinar ou até excluir commits.

### Passo 1: Identificar o Commit Base

Você precisa iniciar o rebase a partir do commit **anterior** ao que deseja editar. Se seu commit problemático é `abc1234`, você deve iniciar o rebase no commit imediatamente anterior a ele.

No nosso exemplo, o commit anterior era `def5678`:

```bash
git log --oneline -5
# 9ab0def feat: adiciona modo escuro
# 7cd8e91 docs: atualiza documentação da API
# abc1234 fix: corrige validação de formulário  ← Este que queremos editar
# def5678 refactor: reorganiza estrutura de pastas  ← Iniciamos o rebase aqui
# 1234abc feat: adiciona autenticação de usuários
```

### Passo 2: Iniciar o Rebase Interativo

Execute o rebase interativo marcando o commit para edição:

```bash
GIT_SEQUENCE_EDITOR="sed -i 's/^pick abc1234/edit abc1234/'" git rebase -i def5678
```

**Explicação do comando:**
- `GIT_SEQUENCE_EDITOR`: Define um editor automático que substitui `pick` por `edit` no commit específico
- `git rebase -i`: Inicia o rebase interativo
- `def5678`: O commit base (anterior ao que queremos editar)

Você verá uma mensagem como:

```
Stopped at abc1234... fix: corrige validação de formulário
You can amend the commit now, with

  git commit --amend

Once you are satisfied with your changes, run

  git rebase --continue
```

### Passo 3: Remover os Arquivos Indesejados

Agora que o rebase parou no commit que queremos editar, podemos remover os arquivos indesejados da [staging area](https://git-scm.com/book/pt-br/v2/Come%C3%A7ando-O-B%C3%A1sico-do-Git#_the_three_states):

```bash
git reset HEAD^ -- CHANGELOG.md TODO.md docs/README.md scripts/test-data.js
```

**Explicação do comando:**
- `git reset HEAD^`: Remove arquivos do commit atual
- `--`: Separador entre opções e nomes de arquivos
- Lista de arquivos: Os arquivos específicos que queremos remover

### Passo 4: Refazer o Commit

Agora refaça o commit sem os arquivos indesejados:

```bash
git commit --amend --no-edit
```

**Explicação:**
- `--amend`: Modifica o último commit
- `--no-edit`: Mantém a mensagem de commit original

Você verá a confirmação:

```
[detached HEAD 4f7a9b2] fix: corrige validação de formulário
 3 files changed, 12 insertions(+), 8 deletions(-)
```

Perfeito! Agora o commit tem apenas os 3 arquivos que deveriam estar lá.

### Passo 5: Continuar o Rebase

Finalize o rebase para aplicar as mudanças:

```bash
git rebase --continue
```

O Git automaticamente atualizará os commits subsequentes e você verá:

```
Successfully rebased and updated refs/heads/main.
```

### Passo 6: Verificar o Resultado

Confirme que tudo está correto:

```bash
git show --name-status 4f7a9b2
```

E verifique o status dos arquivos removidos:

```bash
git status
```

Os arquivos removidos do commit agora aparecem como **untracked** (não rastreados):

```
Arquivos não monitorados:
  CHANGELOG.md
  TODO.md
  docs/README.md
  scripts/test-data.js
```

Eles continuam no seu diretório de trabalho, mas não estão mais no histórico do Git. Você pode commitá-los separadamente quando quiser ou adicioná-los ao `.gitignore`.

## Forma Alternativa: Sem Usar sed

Se você preferir uma abordagem mais manual, pode fazer o rebase interativo tradicional:

```bash
git rebase -i def5678
```

Isso abrirá seu editor padrão (vim, nano, etc.) mostrando:

```
pick abc1234 fix: corrige validação de formulário
pick 7cd8e91 docs: atualiza documentação da API
pick 9ab0def feat: adiciona modo escuro
```

Altere manualmente `pick` para `edit` na linha do commit que deseja modificar:

```
edit abc1234 fix: corrige validação de formulário
pick 7cd8e91 docs: atualiza documentação da API
pick 9ab0def feat: adiciona modo escuro
```

Salve e feche o editor. O resto do processo é idêntico aos passos 3-6 acima.

## ⚠️ Cuidados Importantes

### 1. 🚨 **Nunca reescreva histórico público**

Se você já fez `git push` do commit para um repositório compartilhado (GitHub, GitLab, etc.), **não reescreva o histórico** a menos que:
- Você esteja trabalhando sozinho no branch
- Todos os colaboradores estejam cientes e concordem
- Você esteja disposto a fazer um `git push --force`

Reescrever histórico público pode causar problemas sérios para outros desenvolvedores que já baixaram seu código.

### 2. 💾 **Faça backup antes**

Antes de fazer rebase, sempre é bom criar um branch de backup:

```bash
git branch backup-antes-rebase
```

Assim, se algo der errado, você pode voltar:

```bash
git reset --hard backup-antes-rebase
```

### 3. 🔄 **Commits posteriores serão reescritos**

Quando você edita um commit no meio do histórico, todos os commits posteriores terão seus [hashes SHA-1](https://git-scm.com/book/pt-br/v2/Funcionamento-Interno-do-Git-Objetos-do-Git) alterados. Isso é normal e esperado, pois o hash é calculado com base no conteúdo do commit e seu histórico.

No nosso exemplo:
- **Antes:** `abc1234` → `7cd8e91` → `9ab0def`
- **Depois:** `4f7a9b2` → `a3b2c1d` → `e5f6g7h`

### 4. ⚔️ **Conflitos podem acontecer**

Se houver conflitos durante o rebase, o Git pausará e pedirá para você resolvê-los:

```bash
# Resolver conflitos manualmente
git add <arquivos-resolvidos>
git rebase --continue
```

Se quiser desistir do rebase:

```bash
git rebase --abort
```

## Alternativa Mais Simples para o Último Commit

Se o commit que você quer editar é o **último commit** (HEAD), o processo é muito mais simples:

```bash
# Remover arquivos do último commit
git reset HEAD^ -- arquivo1.txt arquivo2.txt

# Refazer o commit
git commit --amend --no-edit

# Ou com nova mensagem
git commit --amend -m "Nova mensagem"
```

Não precisa de rebase nesse caso!

## Comandos Úteis Relacionados

### Ver diferenças entre commits

```bash
git diff <commit1> <commit2>
```

### Ver apenas nomes dos arquivos modificados

```bash
git diff --name-only <commit1> <commit2>
```

### Ver histórico de um arquivo específico

```bash
git log --follow -- caminho/do/arquivo.rb
```

### Desfazer último commit mantendo as mudanças

```bash
git reset --soft HEAD^
```

### Desfazer último commit descartando as mudanças

```bash
git reset --hard HEAD^
```

## Quando Usar Cada Abordagem

| Cenário | Solução | Complexidade |
|---------|---------|--------------|
| Último commit (HEAD) | `git reset HEAD^ + git commit --amend` | ⭐ Fácil |
| Commit no meio do histórico | `git rebase -i` | ⭐⭐ Médio |
| Já fez push | Evite reescrever, ou use `--force` com cuidado | ⭐⭐⭐ Risco alto |
| Dividir um commit em vários | `git rebase -i` com `edit` + múltiplos commits | ⭐⭐ Médio |
| Combinar múltiplos commits | `git rebase -i` com `squash` ou `fixup` | ⭐⭐ Médio |

## Resumo do Processo Completo

```bash
# 1. Identificar o problema
git log --oneline -10
git show --name-status <hash-do-commit>

# 2. Iniciar rebase marcando commit para edição
GIT_SEQUENCE_EDITOR="sed -i 's/^pick <hash>/edit <hash>/'" git rebase -i <commit-anterior>

# 3. Remover arquivos indesejados
git reset HEAD^ -- arquivo1.txt arquivo2.txt arquivo3.txt

# 4. Refazer commit
git commit --amend --no-edit

# 5. Continuar rebase
git rebase --continue

# 6. Verificar resultado
git log --oneline -5
git status
```

## Conclusão

O `git rebase -i` é uma ferramenta poderosa para manter seu histórico de commits limpo e organizado. Lembre-se dos pontos principais:

- ✅ Use `git rebase -i` para editar commits no meio do histórico
- ✅ Combine com `git reset HEAD^` para remover arquivos específicos sem perder outras mudanças
- ⚠️ Nunca reescreva histórico já compartilhado (a menos que todos concordem)
- 💡 Faça backup antes com `git branch backup-antes-rebase`

Dominar essas técnicas permite que cada commit represente uma mudança lógica e coerente, facilitando code review, debugging e colaboração em equipe.

**Dica final:** Antes de dar `git push`, sempre revise o que está sendo commitado com `git show` ou `git diff --staged`. Prevenir é melhor que remediar!
